# 知識回答を出すかの判定を、判断器ごとに比べた結果(2026-10-21)

研究テーマA(#56)の最初の測定である。知識回答(System1)を出すかどうかを、cosineの閾値の代わりに判断器で決められるかを確かめた。判断器の候補は [判断モデルの比較調査](../plans/2026-10-21-decision-model-survey.md) の5章から、ローカルで動くものを選んだ。

結論を先に書く。どの判断器もcosineを上回らなかった。原因は知識単位の中身が薄すぎることにあり、どの単位もデータ系の質問に答えられる内容を含んでいなかった。今のデータでは、この比較から判断器の良し悪しは決められない。

## 1. 準備

evo-x2のDBに、18トピックそれぞれの新しい日報15件から知識単位を抽出した。LLMはllama-serverのQwen3.6-35B-A3B(json_schema方式)である。221件を保存し、埋め込みを付けて全件を承認した。「システム開発・API」と「パフォーマンスチューニング」の30件は、日報の本文が「APIの設計・実装を行った。」のような1文だけで、LLMが事例として抜き出せないと判断した。このため知識単位は16トピック分になった。

この221件で `scripts/research_knowledge_falsefire.py` を流し、cosineの閾値ごとの発火を測り直した。

| 閾値 | 人に回すべき質問での誤発火 | データ系の質問で発火 | うちトピック一致 | 答えない質問での誤発火 |
|---|---|---|---|---|
| 0.15 | 0.408 | 0.565 | 0.435 | 0.133 |
| 0.20 | 0.122 | 0.435 | 0.391 | 0.067 |
| 0.25 | 0.041 | 0.217 | 0.217 | 0.000 |
| 0.30 | 0.000 | 0.000 | 0.000 | 0.000 |
| DGX 0.20(230件) | 0.184 | 0.391 | 0.304 | |

DGXのときと同じく、誤発火を抑える閾値では発火そのものが止まる。

## 2. 比べ方

`scripts/research_knowledge_judge.py` を使った。評価セット87行それぞれで、最上位の知識単位を1件取り、質問と組にする。判断器は組ごとに「この知識ケースで質問に直接答えられるか」の点数を付ける。判定の基準の文は、以前の `research_knowledge_llm_gate.py` と同じにした。

| 判断器 | 点数の出し方 |
|---|---|
| cosine | 質問と知識単位の埋め込みのcosine(今のやり方) |
| qwen3.6-yesno | llama-serverのQwen3.6に yes / no の一語で答えさせ、最初のトークンの P(yes) / (P(yes) + P(no)) を取る |
| reranker-0.6b / 4b | Qwen3-Reranker。モデルカードの書式で、最後の位置の yes と no のロジットから P(yes) を取る。CPUで動かした |
| sokudan | sokudan-ja-310m の bool 型。温度較正済みの P(true) |

正例はデータ系の行(documentとprior_answerの23行)、負例は人に回す行(49行)と答えない行(15行)である。ROC-AUCにはbootstrap 1,000回の95%信頼区間を付けた。発火率は5分割の交差検証で出した。各行の発火は、その行を含まない4分割で「誤発火率が上限以下で、発火が最も多くなる閾値」を決めて判定している。

## 4. なぜ判断器が効かなかったか

組を1件ずつ見ると、知識単位がどの質問にも答えられる中身を持っていなかった。

- 221件のすべてで「結果」の欄が空である。「打ち手」は平均19文字で、「月次決算に向けた資料作成を行った」のように、何をしたかの見出ししかない
- 元の日報は本文の中央値が17文字で、もともと1文しか書かれていない。会話履歴(2,000行)も平均20文字で、同じく薄い
- データ系の行の多くは、FGX90やSGD450のような型番の障害対応で、文書で答える質問である。日報由来の知識単位にはその内容が無く、最上位には「VPN・ネットワーク構築を提案した」のような一般的な単位が来る

このため、Qwen3.6は正例の組にもほとんど「no」を返した。87組のうち、P(yes)が0.5を超えたのは1組だけである。判定としては正しい。正解ラベルの「データ系の行は答えられる」は文書や過去の回答を前提にしており、今の知識単位では成り立たない。cosineがやや良く見えるのは、「同じトピックの単位が見つかるか」を測っていて、それがラベルと相関するからだろう(推定)。

## 5. 次に試すこと

判断器を比べる前に、答えを含む知識単位を用意する必要がある。候補は次の3つ。

1. 文書と過去の回答から知識単位を抽出する。データ系の行が前提にしている情報源なので、ラベルと中身がそろう
2. 正例のラベルを付け直す。組ごとに「この単位で本当に答えられるか」を人が判定し、そのラベルで比べる。87組なので手作業で間に合う
3. 外部APIの判断モデル(Jev、Microsoft-Decision-1)は、1か2のあとで加える。今の組では、どのモデルでも結果は変わらない見込みが高い
