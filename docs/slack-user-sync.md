# Slack ディレクトリ同期（#406 step 3）

Slack ワークスペースを**社員名簿の正**とし、`slack_links` をそれに突き合わせる。

**既定は無効。** 有効化の前に下の「有効化してよい条件」を読むこと。

---

## ⚠️ 有効化してよい条件

**Slack がくれるのは「人」であって「証拠」ではない。**

推薦のスコアは証拠（有用な回答 1.0 / 過去の回答 0.7 / 直接相談のふりかえり 0.25）から
組み立てられるが、**Slack のプロフィールからはこのどれも取れない**。名前・メール・肩書き止まり。
（資格・案件・自己申告スキルは #95 で根拠から外した）

したがって、証拠の取り込み（#404）より先に全員を登録すると、
**`topic_fit = 0` の社員が N 人**できる。候補だけ増えて信号がゼロなので、
**画面は賑やかになるのに推薦は悪くなる**。#401 が全社規模で起きる形。

→ **`TEKIJIN_SLACK_USER_SYNC_ENABLED=true` にするのは、追加される人の証拠が入ってから。**

---

## 何をするか / しないか

| | 動作 |
|---|---|
| ✅ | メールアドレスが一致する**既存の社員**に Slack アカウントを結びつける |
| ✅ | Slack で**無効化された**アカウントの link を外す（＝Slackログインが止まる） |
| ✅ | 同時に**推薦候補から外す**（`is_active=false`・#506）。取り次ぎが届かない相手を勧めないため |
| ⚙️ | **社員行を作る**（`TEKIJIN_SLACK_USER_SYNC_CREATE_EMPLOYEES=true` のときだけ）。既定は作らず報告のみ |
| ❌ | **社員行を削除しない。** 質問・回答・証拠が参照しているので、退職しても行は残す |

### 退職の扱いが2段になっている理由（#506）

link を外すだけでは**ログインが止まるだけ**で、**推薦は止まりません**。候補プールは
`nodes.py` の `_candidate_pool` → `list_employees()` ＝**全社員**で、証拠起点ではないからです。
退職者が「この人に聞くとよい」と出て、取り次いでも**届かない**（届ける link を今まさに外したので）。

そこで `employees.is_active` を落として候補プールから外します。**行は残す**ので、
その人が書いた質問・回答の著者名は履歴に出続けます。`get_employee` は絞り込みません。

`is_active` の既定は **true**（列にもDDLにも）。合成の40名は列より古く、
既定を false にすると**推薦が空になり eval が全滅**します。

### 社員の自動作成について（既定OFF）

`make seed` は全テーブルを TRUNCATE するので、**人を1人足す非破壊の経路が存在しませんでした**（#402）。
そのため Slack に入った新人は連携もログインもできませんでした。これを埋めるのがこのモード。

- 作られた社員は **`password_hash` が NULL** ＝ Slackログイン専用。推測できる資格情報を作らない
- **id は自動採番に任せない。** `make seed` は `TRUNCATE ... RESTART IDENTITY` の後に
  id 1..40 を**明示挿入**するため、シーケンスは 1 のまま `max(id)` が 40 になる
  （本番DBで実測: `last_value=1` / `max(id)=40`）。自動採番だと **id=1 で田中太郎と衝突する**ので、
  挿入前に `setval` でシーケンスを揃える
### ⚠️ 自動作成の残存リスク: 未入社者のアドレスの先取り

**これは塞げていません。** 有効化の判断材料として明記します。

1. 攻撃者（ワークスペースの正規メンバー）が、**まだ TEKIJIN に居ない人**のアドレス
   （例: 入社予定者の会社アドレス）を自分の Slack プロフィールに入れる
2. 次の同期で、そのアドレスの社員行が**作られ、攻撃者の Slack アカウントに紐づく**
3. 本人が後から Slack に参加しても、**`already_linked_to_another_slack_account` で永久に弾かれる**

実証済み（planner のみ・DB不要）:

```
run1  create : (('future.hire@corp.jp', 'なりすまし', 'U_ATTACKER'),)   skipped: {}
run2  link   : ()   create: ()   skipped: {'already_linked_to_another_slack_account': 1}
```

「既存の link は上書きしない」規則は**既存社員を守る**ためのもので、
**まだ存在しない人を守る規則ではありません**。同じ回の中の競合（`ambiguous_email`）は
塞いでありますが、これは**回をまたぐ・主張者が1人**なので、その仕組みでは捕まりません。

**復旧は手作業のみ**（該当行の付け替えか削除）。自動検知はありません。

**緩和策:**

- `TEKIJIN_SLACK_USER_SYNC_ALLOWED_DOMAINS` で**会社ドメインに限定する**。
  社外ドメイン（gmail 等）からの作成は止まりますが、**会社ドメイン内の先取りは止まりません**
- 作成は `INFO` ログに**必ず1行出る**（社員ID・メール・Slack ID）。有効化するなら**ログを見る運用にする**
- **Slack のメールが検証済みである（SSO/SCIM 運用である）ワークスペースでのみ有効化する。**
  これが本質的な前提条件です

- ⚠️ **作っただけでは推薦されません。** 証拠ゼロ＝`topic_fit=0` なので上位に来ない（#401）。
  「Slackにしか居ない人が推薦される」には **#404（実Slack→証拠）** が要る

### 触らないもの（セキュリティ上、意図的）

OAuth の連携フローは**同じ脆弱性クラスを3回**踏んでいる。本質は
**「2つの半分が別人のもの」**だった。この同期は**人間の同意が1つも介在しない**まま
同じ `slack_links` を書くので、同じ規則を構造として持たせてある。

| 規則 | 理由 |
|---|---|
| **既存の link は上書きしない** | 再連携はベアラトークンを伴う意図的な操作。同期にその同意は無い。Slackログイン有効時、上書きは**セッションの乗っ取り**になる |
| **他人に紐づく Slack アカウントを付け替えない** | 上の鏡像。OAuth 1周目の欠陥をそのまま自動実行することになる |
| **`deleted: true` のときだけ link を外す** | 一覧からの**不在では外さない**。ページが途中で切れただけで「全員退職」と読めてしまう |
| **外す対象は Slack ID で引く**（メールではない） | 実際にその Slack アカウントを持つ行だけを切る |
| **メールが無ければ対象外** | 表示名での曖昧一致を認証経路に持ち込まない |
| **管理者アドレスは連携しない** | 管理者は意図的に社員行ではない。Slack から継承させない |
| **1回の同期で2人が同じ社員を主張したら、どちらも連携しない** | 上の規則は全て「同期前のDB」を見ている。**同じ回の中での衝突は素通りする**。SSO/SCIM が無い Slack では `profile.email` は本人が自由に設定できるので、**同僚のアドレスを自分のプロフィールに入れるだけ**で到達できる。先着を採ると「攻撃者は先に並べばよい」だけになり、どちらが本物かはここからは判別できない |
| **1つの Slack アカウントが2人の社員を主張したら、どちらも連携しない** | 上の鏡像。適用すると `slack_user_id` の UNIQUE に途中で当たり、**バッチ全体がロールバックされて退職者の link 解除まで巻き添えになる** |

判断は `backend/src/tekijin/slack/user_sync.py`（純関数・DBもネットワークも触らない）に集約してある。
DB を書くのは `backend/src/tekijin/data/slack_directory.py` だけで、こちらは判断しない。

## セットアップ

### 1. Slack App にスコープを足す

**Bot Token Scopes** に以下を追加して**再インストール**する。

```
users:read
users:read.email     ← これが無いと profile.email が返らず、誰一人マッチしない
```

### 2. `.env`

```bash
TEKIJIN_SLACK_BOT_TOKEN=xoxb-...
TEKIJIN_SLACK_TEAM_ID=T...          # 空だと同期は 503 で拒否する
TEKIJIN_SLACK_USER_SYNC_ENABLED=true
```

`TEKIJIN_SLACK_TEAM_ID` が空のときに走らせると、planner は**誰にも一致しない**。
それは「同期すべき人が居なかった」と見分けがつかないので、**走らせずに 503 で断る**。

### 3. 実行

```bash
curl -X POST http://127.0.0.1:18000/slack/sync-users \
  -H "Authorization: Bearer <管理者のトークン>"
```

```json
{"linked": 3, "unlinked": 0, "skipped": {"no_matching_employee": 12, "not_a_member": 4}}
```

`skipped` は**レスポンスに含める**。健全な同期はほとんどの回で何も変えないので
「0 件」だけでは情報にならず、**`no_email` が全員分**なら
`users:read.email` の付け忘れだと分かる。

### 4. 定期実行（cron）

```cron
17 * * * * curl -fsS -X POST http://127.0.0.1:18000/slack/sync-users -H "Authorization: Bearer $TEKIJIN_ADMIN_TOKEN" >>$HOME/slack-sync.log 2>&1
```

1時間おきで十分（取りこぼしても次回で復旧する）。

> **アプリ内のタイマースレッドにしていない理由。**
> このコードベースでは、デーモンスレッドが例外を飲み込んで
> **主キー重複で失敗し続けていたのに誰も気づかなかった**ことが実際にある
> （`create_channel_link`）。この同期は「誰がログインできるか」を決める表を書くので、
> 失敗が黙って消える場所に置かない。エンドポイントなら、失敗にステータスコードと
> 呼び出し元という**行き先**がある。

## 対応表

| Slack | TEKIJIN |
|---|---|
| 一般メンバー・メール一致 | link を作る |
| 一般メンバー・該当社員なし | 既定 `no_matching_employee`（作らない）／作成モードON なら**社員行＋link を作る** |
| ボット / Slackbot | `not_a_member` |
| ゲスト（`is_restricted` / `is_ultra_restricted`） | `not_a_member`。社外の人にセッションを渡さない |
| メール未取得 | `no_email`（スコープを疑う） |
| 別ワークスペース | `foreign_workspace` |
| 同じ社員を2人以上が主張 | `ambiguous_email`（**どちらも連携しない**） |
| 同じ Slack ID が2人の社員を主張 | `ambiguous_slack_account`（同上） |
| 無効化済み（`deleted: true`） | link を外す（行は残す） |

---

## 既知の制限

- **作られた新人はまだ推薦されない。** 証拠がゼロなので `topic_fit = 0`。
  #404（実Slackのやり取りから証拠を抽出）が入って初めて候補として浮上する。
- **異動・改名は追わない。** 追うのは在籍/退職と link だけ。部署の変更は反映されない。
