# RAG 改善の方向性（TEKIJIN 版）

社内 QA / 知識活用における RAG の一般的な知見（社内資料 *20231217_RAG に関する知見* より）を、
TEKIJIN の実測結果に接続してまとめる。**結論から言うと、TEKIJIN の系統②（取次ぎ）の算法的改善は
実力天井に達しており（[ADR-0008](../adr/0008-system2-hit3-ceiling-and-augmentation-negatives.md)）、
この先の伸びしろは「渡す情報の質」＝暗黙的情報の付与とデータ拡充にある。** RAG 知見の中心命題と一致する。

## 0. RAG 一般論の骨子（参考資料の要約）

改善は3つの方針に分かれる。

- **方針1: いいモデルを使う**（`情報が十分にあれば人間並みに答えられる`）。
- **方針2: プロンプト全体を工夫する**（構成・要素・形式）。
- **方針3: 関連情報の渡し方を工夫する** ← エンジニアリングの主戦場。「量」と「質」に分かれる。
  - 3-1 **量**: 取り出す件数を増やす（10 件目安・20 件も可）、検索仕様の見直し、圧縮（ただし latency 悪化で体験が落ちる）。
  - 3-2 **質**: テキストの取り出し方の改良（前処理）、そして **暗黙的な情報の追加**。

**中心命題（最重要）**: システムが答えに使える情報は、人間が使う情報の**ごく一部**（明文化された文書）に
過ぎない。業務知識・社内知識・業界常識の多くは**暗黙知**で、システムには入らない。だから
**PoC レベルの実装は「80 点くらい」が限界**で、これは評価項目を設計するときの前提にする。
「高度な認知は人に委ね、自動化しやすく煩雑な所をシステム化する。1 種の諦めも大事」。

## 1. TEKIJIN の現在地（実測）

- 系統②の実 E2E Hit@3 ≈**0.79**（#405 qsim 後・[eval-metrics.md](../benchmarks/eval-metrics.md)）。person recall は 1.000。
  律速は **C1 トピック予測 acc@1 ≈ 0.75**（候補プール recall 0.952＝正解はほぼプールに居る）。R@3 0.90 は未達。
- 算法レバーの多く（クエリ拡張 #371 / union 採点 #380 / C1 few-shot #384）は実 E2E を robust に超えられなかったが、
  **#405 qsim（質問↔過去回答の意味一致）は例外＝実 E2E Hit@3 0.742→0.788 の唯一の勝ち**（既定ON）。C1 が誤トピックの行を
  質問特異的加点で救う。飽和した `topic_fit`（タグのみ・ADR-0006）とは別軸。
- 系統①（自己回答）は有効化済。**#291 データ由来経路**に加え、**#413 additive で person 経路でも引用を取次ぎと併記**（既定ON・
  floor 0.20）。#433 で日報も知識源にしたが、#91 で日報の機能ごと削除した。grounded ≈ 0.261 とまだ低いのが伸びしろ。
- 系統③（蓄積）は**骨格実装済（#357/#448）**: `knowledge_units` テーブル＋抽出パイプライン（`extract.py`／
  チャット `chat.py`・オフライン。日報からの抽出は #91 で削除）。合成チャットは抽出0件（データの限界・手法は正）＝実データ待ち。

## 2. RAG 知見 → TEKIJIN の具体レバー（優先度つき）

算法でなく**データ/情報の質**を上げる方向。上ほど効果が見込め、かつ TEKIJIN の構造に合う。

### (A) 暗黙的情報の付与（方針3-2-2）＝ 最大の伸びしろ

RAG 資料が「一番効く」とする領域。TEKIJIN に落とすと:

- **質問に付随する文脈**: 質問者と回答者の関係性、スレッド内の会話、**回答者が過去に答えた/質問した内容**、
  経緯。**#405 qsim で「回答者が過去に答えた内容」の意味一致は C6 に実装済（既定ON）**。
  `employee_chat_history`（2000 行）は #448 で会話単位の**知識抽出**の入口に（生chatはノイズなので抽出が前提）。
  日報は #433 で知識源にしたが、#91 で機能ごと削除した。
- **メタデータ**: 作成者・日時・部署・出典パス。TEKIJIN は self_answer で既に**出典（doc/qa）を付与**しており
  （RAG 資料の「メタデータ＝ファイルパスを付ける」に対応・実装容易で効果高い）、これを人物推薦の
  reasons にも広げる余地がある。
- **用語集（glossary）**: 「20 期」「型番」等の社内固有語を展開して検索/プロンプトに付与する。TEKIJIN の
  **型番 eval（#296）**はこの領域。用語を正規化してからトピック照合・検索に回すと、C1 の取りこぼし
  （語彙不一致 #116）を機械的に救える可能性がある。※ ただし RAG 資料も「網羅性・暗黙知の多さ」で
  難しいと注記。

### (B) 系統③（蓄積）＝ 暗黙知を明文化する仕組み

RAG 資料の「作成者/管理者に明文化してもらう」を、TEKIJIN では**回答そのものを蓄積して自動明文化**する形で
実現できる。回答本文の捕捉 → `answers` 行作成 → 埋め込み → 将来の self_answer が引く、という
**回答→蓄積→自己回答ループ**（#274）。self_answer を有効化した今、これを閉じると母集団が経時的に育つ。
#357 知識フレームワーク（生データ→構造化ケース）も同じ「明文化」の軸。

### (C) 接地検出 UX（体験・安全）

RAG 資料の「ドキュメントを使っていないケースを検出して明示する」（`この回答はドキュメントに
基づいていないようです`）。TEKIJIN の self_answer は既に **grounded / not-grounded を判定**しているので、
grounded=false のときに「一般論であり社内知識に基づかない」旨を UI に出すのは低コストで効く。
出典リンク描画は ResultScreen まで対応済み（#382）。

### (D) 検索の「量」（方針3-1）＝ TEKIJIN では慎重に

RAG 資料は「10→20 件」「ファイル分割」を勧めるが、これは**文書 QA（多く読ませて compose）**の話。
TEKIJIN の系統②は**人物ランキング**で、候補を増やすと低精度シグナルが順位を汚す（union #380 が悪化した
のと同型）。→ **document / self_answer の compose 側では有効**（証拠を多く渡す）だが、**person 順位付けでは
単純な件数増はしない**。前処理（日報・チャットの証拠化）で「質」を上げる方が筋。

## 3. やらない/慎重にやること（実測に基づく）

- **算法での系統② Hit@3 改善**（クエリ拡張・union 採点・C1 few-shot の再挑戦）。実測で robust な
  改善なし・routing 破壊やノイズ悪化のリスク（ADR-0008）。C1 品質はプロンプトでは動かない。
- **fine-tuning で知識を入れる**。RAG 資料の通り「知識だけ学習は難しく、会話調を学んで回答が壊れる」
  「評価・汎用性が不透明」。RAG（＝検索で知識を渡す）の方が分析・検証しやすく出典も出せる。
- **単発 run の小さな差で判断する**。C1 は run 間 ±0.09 振れる（eval-metrics.md §3）。

## 4. 評価設計への含意

「80 点天井」を顧客・関係者と**合意**し、評価項目もそれ前提で組む。RAG 資料の
**"G 不要論"（検索/取次ぎ部分だけを提供するのも正当）**は、TEKIJIN の「答えられないものは人に取り次ぐ」
（person recall 1.000）を裏付ける。完璧な自己回答を目指すより、**接地できるものは出典付きで答え、
できないものは確実に人へ繋ぎ、その知識を蓄積する**という三系統の役割分担が、天井を踏まえた正しい設計。
