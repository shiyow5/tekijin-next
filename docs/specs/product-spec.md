## 1. コンセプト

> **暗黙知を、使った分だけ形式知に変える。**
> AIでも、形式化されていない知識（暗黙知）には答えられない。TEKIJIN は、その暗黙知を
> **「人に聞く」という行為の履歴として蓄積し、共有できるノウハウ（形式知）へ変換し続ける**基盤である。
> 答えは、**記録にあればその出典から、無ければ人から**引き出す。AIが根拠なしに答えを作ることはなく、
> 出典を示せないときは答えずに適任者へ取り次ぐ。取次ぎで得た答えは記録に変え、次からは自己回答に回す。

### 何をするアプリか

1. **暗黙知は人の中にある。** 誰が何に詳しいかは名簿に載っていない。TEKIJIN は回答・案件・日報という
   "行動の痕跡"から専門性を推定し、必要な瞬間に正しい人へ繋ぐ（人への取次ぎ）。
2. **聞くたびに形式知が1つ増える。** 人に聞いて得た答えは、そのまま「誰が・何に・どう答えたか」という
   構造化された記録として蓄積する。使い続けるほど、共有されるノウハウが増える。
3. **既存のノウハウは取り込む。** 社内のコミュニケーションツールや日報に埋もれた知識を変換して初期資産にする。
4. **蓄積した知識が次の人を助ける。** 同じ問いには過去の記録が先に立ち、人を介さず自己解決できる。
   誰が答えたかは必ず残る（QAボット化しない）。

これによって、今まで形になっていなかった知識が、使った分だけ形になって共有され、組織全体の成長を促す。

### 人への取次ぎは「主軸を回す手段」

人を推薦して繋ぐことは目的そのものではなく、**暗黙知を引き出して記録に変えるための入口**である。
「文書を読んで答える」QAボットと異なるのは、探す対象（人）・動かすデータ（行動痕跡・蓄積される知識）・
設計の向き（両側）の3点。取次ぎで得た一次情報が、次からの形式知になり、使うほど資産が増える。

> **用語の整理（主線 と 主軸 は別レイヤ）。**
> **主線**＝解決経路の判定（C5）における既定ルート＝**人への取次ぎ**（対する 補助＝過去回答の提示 /
> 格下げ＝文書の場所提示）。「1問をどの経路で解くか」の話。
> **主軸**＝プロダクト全体の目的＝**ナレッジ蓄積（暗黙知→形式知）**。「何のためのアプリか」の話。
> 両者は競合しない —— **主線（人への取次ぎ）は、主軸（蓄積）を回すための手段**である。

### 解決する課題

| 課題ID | 内容 |
| --- | --- |
| T-01 | 誰が何に詳しいか分からない |
| T-02 | 「こんなことを聞いていいのか」という遠慮で質問できない |
| T-04 | 相談の成立が「先輩の在席」と「先輩からの声かけ」に依存している |

## 2. ユーザーと、それぞれの Before / After

### 聞く側 — 営業1年目の人など

| | Before | After |
| --- | --- | --- |
| 相手を探す | 先輩に「これ誰に聞けば」と聞く。先輩が外出なら待つ | 質問を打つと候補が3名、根拠つきで出る |
| 聞き方 | 失礼のない依頼文を推敲して20分 | 下書きが出る。直して送るだけ |
| 外した時 | たらい回し。半日消える | 断られたら自動で次の候補へ回る |
| 二度目の質問 | 同じことを二度聞くのが怖くて自分で調べる | **過去に自分が受けた回答が出てくるので、聞かなくて済む** |

### 聞かれる側 — SEなど

| | Before | After |
| --- | --- | --- |
| 届く質問 | 情報が3行。3往復してやっと本題 | 必要項目が埋まった状態で届く |
| 忙しい時 | 断りづらいので後回しにする | 「今は難しい」を押すと次の候補へ回る |
| 同じ質問 | 別の営業から何度も来る | **一度答えた内容が次から自動提示され、来なくなる** |
| 見返り | 何も残らない | 「あなたの回答が◯人に再利用されました」 |

### 取次ぎ役 — 人事など

| | Before | After |
| --- | --- | --- |
| 役割 | 人間ルーター。帰社すると若手3名が並ぶ | 取次ぎだけの質問が来なくなる |
| 心配 | 聞きに来ない子の状況が分からない | 質問が解決されずに滞留していると分かる |

## 3. 主線のユースケース

```
① 疑問を持った人が質問を打つ
   「お客様がUTMの入れ替えを検討中。他社製品からの移行で注意点は?」
              ↓
② AIが不足に気づき、逆質問する
   「現行の製品と、対象の拠点数を教えてください」
              ↓
③ 質問者が追記。AIが解決経路を判定（人への取次ぎが主線）
              ↓
   ┌──────────────────┬──────────────────────┐
   │ 主線 人に取り次ぐ       │ 補助 過去に"誰が"答えたか   │
   │ （expertise location）  │ を人の証拠として提示        │
   └──────────────────┴──────────────────────┘
   （文書に明確な記載がある場合のみ、答えず"場所"を指し示す＝格下げ）
              ↓（主線）
④ 候補3名を根拠つきで提示
   ○○さん（技術部）適合度82%
     ├ 資格: 情報処理安全確保支援士
     ├ 類似の質問に過去5件回答
     └ 直近3か月に同種案件を2件担当
              ↓
⑤ 下書きが生成される。質問者が直して送信
              ↓
⑥ 候補者が「今は難しい」→ 自動で第2候補へ
              ↓
⑦ 第2候補が回答。2第候補者に届く
              ↓
⑧ その回答が専門性グラフに取り込まれ、次の同じ質問は補助経路で「最初の候補者が詳しい」と即提示される
```

**⑧が主軸。** 1回の取次ぎで得た回答は、そのまま形式知として蓄積される。回答が溜まるほど
「誰が何に詳しいか」が正確になり（＝使うほど育つグラフ）、同じ問いは次から人を介さず解ける。
**取次ぎ（①〜⑦）は、この蓄積（⑧）を回すための入口**である。

## 4. 機能一覧

### 必須

| ID | 機能 | 概要 |
| --- | --- | --- |
| F-01 | 質問入力 | テキスト1欄。音声入力も可 |
| F-02 | 意図理解・トピック抽出 | 質問から領域・製品・状況を構造化 |
| F-03 | **逆質問** | 情報が不足していれば、AIが聞き返す |
| F-04 | 解決経路の判定 | **データで答えられるか（自己回答）／人に取り次ぐか**を確信度で判断（C5）。データ由来（過去回答・文書）は C7' の自己回答へ。**人へ取り次ぐ場合でも、根拠があれば引用付き回答を取次ぎと併記（#413 additive・既定ON）** |
| F-05 | 人の推薦 | 上位3名を適合度と根拠つきで提示。**行動痕跡から推定した専門性が根拠**。この案の中核 |
| F-06 | 依頼文の下書き生成 | 相手の職種・関係性に応じた文面 |
| F-07 | 送信と受信 | 聞く側／聞かれる側の画面 |
| F-08 | 思考過程の可視化 | AIが今何をしているかを逐次表示（LangGraph の `stream(stream_mode="updates")` を SSE 配信） |

### 重要

| ID | 機能 | 概要 |
| --- | --- | --- |
| F-09 | 断る導線 | 「今は難しい」で次候補へ自動再ルーティング |
| F-10 | 回答のナレッジ化（形式知化） | 回答を「誰が・何に・どう答えたか」の記録として蓄積し、専門性の推定を更新。次から補助経路で「誰が詳しいか」に使う。**本プロダクトの主軸機構** |
| F-11 | 負荷分散 | 推薦スコアに受け入れ余裕度を掛ける |
| F-12 | ダッシュボード | 自己解決率、負荷分散、平均解決時間、蓄積されたナレッジ件数 |
| F-16 | 既存ノウハウの取り込み | 社内のコミュニケーションツールや日報に埋もれた暗黙知を変換し、初期のナレッジ資産にする。**骨格実装済（#357/#448）**: チャット・解決済スレッドから `knowledge_units` へ LLM 抽出（オフライン）。日報からの抽出と日報の知識源化は #91 で削除した。合成チャットは抽出0件（データの限界・手法は正／実データ待ち） |

### 余力があれば

| ID | 機能 |
| --- | --- |
| F-13 | 「あなたの回答が◯人に再利用されました」通知 |
| F-14 | 音声入力（外出中の営業を想定） |
| F-15 | 忙しさモードのトグル |

## 5. 画面仕様

### 画面1: 質問する（聞く側）

```
┌──────────────────────────────────────┐
│  TEKIJIN                        [藤田 悠斗 ▾]  │
├──────────────────────────────────────┤
│                                                    │
│   何を知りたいですか？                             │
│  ┌────────────────────────────────┐│
│  │                                          [🎤]  ││
│  └────────────────────────────────┘│
│                                     [ 聞いてみる ] │
│                                                    │
│   最近あなたが解決した質問                         │
│   ・UTMの移行時の注意点  → 高梨さんが回答          │
└──────────────────────────────────────┘
```

- **入力欄は1つ。** カテゴリ選択やタグ付けをユーザーにさせない
- 分類はAIの仕事。人に分類させた時点で「入力しやすい設計」ではなくなる

### 画面2: 処理中（思考過程の可視化）

```
┌──────────────────────────────────────┐
│  ✓ 質問を理解しました                              │
│      領域: ネットワークセキュリティ / UTM          │
│      状況: 他社製品からの移行                      │
│  ✓ 過去に誰が答えたかを調べました（近い回答2件：0.62）│
│  ⟳ 行動痕跡から、詳しい方を推定しています...       │
└──────────────────────────────────────┘
```

- **裏で賢くても、見えなければ評価されない。** 自律性はここで伝える
- 確信度を数字で出す。「該当なし」も理由つきで見せる

```
│                                                    │

├──────────────────────────────────────┤

│  └────────────────────────────────┘│

```

補助経路（過去に誰が答えたか）の場合（#310）:

候補が1名（過去にその人が同様の質問に回答した実績のみ）になるケースでも、独立した中間画面は挟まない。上記の主線と同じ画面3をそのまま表示し、過去回答の実績は候補カードの根拠リストの1項目（「過去回答: 類似の質問に過去5件回答」等）として見せる。「この方が詳しそうです」だけの根拠専用画面や「この方に追加で聞く」ボタンは廃止し、常に下書き・送信のUIまで到達できるようにする。

- **主役は「人」。** 過去回答は答えではなく「この人が詳しい」という**証拠**として見せる — これは候補カードの根拠リストが担う
- 候補が1名でも、2〜3名のときと同じ画面遷移（結果を見る → 候補カード＋下書き）にする。行き止まりも余分なクリックも作らない

```
│  あなたに届いた質問                    [高梨 健太 ▾]│
├──────────────────────────────────────┤

│                                                    │

│  【希望時期】10月    【予算感】未確定              │
│                                                    │

│  情報処理安全確保支援士 / 同種案件2件 / 類似回答5件│
```

- **必要項目が埋まった状態で届く。** これが下書き機能の本当の受益者
- 「今は難しい」が**回答ボタンと同じ大きさ**。断ることを二級の選択肢にしない
- 最下段の再利用件数が、答えることの見返りになる

### 画面5: ダッシュボード（管理側・デモ用）

| 指標 | 表示 |
| --- | --- |
| 自己解決率 | 補助経路（過去に誰が答えたか）で人を介さず解決した割合の推移 |
| 負荷分散 | 上位1名への集中率（素朴な詳しさ順との比較） |
| 平均解決時間 | 質問から解決までの時間 |
| 推薦精度 | 評価セットに対する Top-1 / Recall@3 |
| **今月の形式知化**（#294） | 当月に新しく形式知になった件数と、前月比 |
| **暗黙知の回収率**（#294） | 承諾された取次ぎのうち、知識が残った割合 |

**蓄積メトリクスの定義**（#294）。「形式知化された知識」として数えるのは、**実行時に生まれたものだけ**:

| 数える | 由来 |
| --- | --- |
| 回答の蓄積 | 取次ぎ先が承諾して回答し、`answers` 行になったもの（#274） |
| 直接相談のふりかえり | 対面相談の書き起こし（#247）。会話ログが無いので、この行自体が知識 |

**初期投入した合成データは数えない。** コーパスには当月日付の回答が16件含まれており、`answers`
表を素朴に数えると、誰も使っていないDBで「今月16件」と出てしまう——主要KPIとして、
**都合のいい方向に間違う**という最悪の壊れ方をする。区別に印は要らない: 蓄積された回答には
必ず承諾済みの `recommendations` 行があり、seed は `recommendations` を**一度も挿入しない**
（TRUNCATE するだけ）。

**回収率を併記する理由**: 件数は増える一方なので、ループが閉じているかを何も語らない。
「承諾された取次ぎのうち、知識が残った割合」は**下がりうる**唯一の値で、そこが見どころ。

> **個人の質問内容は表示しない。** 集計のみ。
> 監視ツールになった瞬間に、誰も本音の質問をしなくなる。

## 6. UX原則

| # | 原則 | 具体 |
| --- | --- | --- |
| 1 | **分類はユーザーにさせない** | 入力欄は1つ。カテゴリ選択もタグ付けもさせない |
| 2 | **待たせるなら、何をしているか見せる** | SSEで思考過程を逐次表示。無反応の5秒は非常に長い |
| 3 | **わからない時は、わからないと言う** | 確信度が閾値未満なら答えを作らず人に回す |
| 4 | **断ることを失礼にしない** | 「今は難しい」を1タップ、回答と同格の大きさで |
| 5 | **行き止まりを作らない** | どの画面にも次の行動がある。補助経路（過去回答）からも人に落とせる |
| 6 | **根拠を必ず出す** | 推薦にも回答にも出典。利用者自身が妥当性を判断できる |
| 7 | **答えた人が損をしない** | 再利用の可視化。同じ質問が二度来ない |
| 8 | **管理側に個人を見せない** | 集計のみ |

## 7. ステークホルダー設計

| 誰 | 得るもの | 奪わないための配慮 |
| --- | --- | --- |
| **聞く側（若手）** | 相手が分かる。下書きがある | 恥をかかせない。二度目の質問も補助経路で静かに解決する |
| **聞かれる側（ベテラン・SE）** | 情報の揃った質問。断れる。回答が資産になる | **負荷を集中させない**（F-11）。監視しない |
| **取次ぎ役（人事）** | 取次ぎだけの質問が来なくなる | 頼られなくなる感を防ぐ。回答の再利用数で貢献を可視化 |
| **営業事務** | 同じ質問が減る | **存在価値を奪わない。** 回答は名前つきで残り、本人の実績になる |
| **管理職** | 組織のどこで詰まっているかが分かる | 個人の質問内容は見せない。評価に使わせない |
| **会社** | 属人知が資産化される | 権限の壁を越えない。合成データでの検証にとどめる |

> **設計上の最重要判断は「営業事務・ベテランから存在価値を奪わないこと」。**
> P2-A 川口佳世のインサイト「属人化は問題だと分かっているが、それが自分の存在価値でもある」に対して、
> 本プロダクトは**置き換えではなく増幅**の立場を取る。
> 「あなたの代わりにAIが答えます」ではなく「**あなたの答えが、書いた回数だけ効くようになります**」。

## 8. やらないこと

| やらないこと | 理由 |
| --- | --- |
| AIが**根拠なしに**自分の言葉で答えを作る | 思想に反する。既存チャットボットとかぶる。自己回答（C7'）は供給された根拠だけから生成し、実在する出典を1つも示せなければ（`grounded=false`）**答えずに**取次ぎへフォールバックする |
| 文書を読んで答える機能**だけ**を主役にする | それだけならQAボットで、新規性が薄れる。自己回答（#291）は主軸である蓄積を消費する側であって、蓄積を作るのは人への取次ぎ。**誰が答えたかが必ず残る**点でQAボットと異なる |
| 個人の質問内容を管理職に見せる | 使われなくなる |
| 実データへの接続 | もらえない。合成データで通す |
| Slack連携 | 認証と権限で時間を食う |
| 本格的な認証・権限管理 | ユーザー切替のモックで足りる |
| 回答の品質を採点する | 別プロダクトになる |
