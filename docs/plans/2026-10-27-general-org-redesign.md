# 任意の組織の知識を蓄積する仕組みへの作り替え(設計案)

2026-10-27 作成。Issue #64。6章の論点は同日にユーザーが決めた。実装は段階R1から別のPRで行う。

## 1. なぜ作り替えるか

TEKIJINはインターン先の1社に向けて作った。社員名簿(部署・役職・資格・案件)、日報、22語のトピック語彙、87行の評価セットはすべてその会社を想定した合成データで、推薦や経路判定の閾値もこのデータで調整してある。インターンが終わり、TEKIJINは個人のプロダクトになった。会社という背景は無くなった。

これからの対象は、DiscordやSlackを中心に会話している任意の組織(サークル、コミュニティ、小さなチームなど)とする。日報や名簿のような整った基本データは無い。手に入るのは、組織の会話と、自己紹介スライド・企画書・マニュアル・引継ぎ書などのGoogle ドキュメント/スライドやNotionページである。

2026-10-27 にユーザーが決めた前提は次の4つ。

| 論点 | 決定 |
|---|---|
| 提供の形 | 1つの組織で始める。テーブルに組織IDを持たせ、複数の組織に広げられるようにしておく |
| 試す組織 | ユーザー自身の組織が実在する。実データはメンバーの同意を取ってから使う |
| 中心の機能 | 蓄積した知識で答え、答えられないときに詳しい人へ繋ぐ |
| Slack | Discordを先に作る。Slackはあとで同じ仕組みにつなぐ |

## 2. 目指す姿

組織のメンバーはDiscordで `/ask` と打つか、Web画面から質問する。TEKIJINは、取り込んだ文書と会話、それに承認済みの知識から答えを探し、見つかれば出典付きで答える。見つからなければ、その話題に詳しそうなメンバーを推薦し、本人に依頼を送る。依頼された人が答えると、その回答は知識の下書きになり、組織の誰かが確認すると知識として使えるようになる。メンバーは `/tekijin add` で文書や知っていることを足せる。管理者(最初はユーザー本人)は、取り込みから外すチャンネルを決め、知識の下書きを確認する。

作らないものもはっきりさせておく。汎用の社内検索エンジンは目指さない。検索だけならNotion AIやOnyxで足りる。LLMの訓練(ファインチューニング)に組織のデータは使わない。100を超えるDiscordサーバーへの配布は当面考えない。

既存の製品と比べたときのTEKIJINの違いは、答えられない質問を、話題ごとに選んだ人へ繋ぐことと、その回答を確認付きで知識に戻すことにある。調査した範囲では、Guru(Ask an Expert)とSlack AI(Channel Expert)がこれに近い機能を持つ。ただ、どちらも有料の企業向けSaaSで、Slack中心である。Onyxは担当者を固定したフォローアップしか持たない。Discordを中心にする組織向けに、質問ごとに人を選び、回答を知識に戻す仕組みは見つからなかった(調査は2026-10-27時点、確認できた範囲での話)。

## 3. 外部の制約

取り込み方は、各サービスの権限モデルと規約で大きく決まる。以下は2026-10-27の調査による。

| 知識源 | 読める範囲 | 変更の知り方 | 個人で運用するときの壁 |
|---|---|---|---|
| Discord | ボットを招待したサーバーで、権限を与えたチャンネル | Gatewayのイベント(常時接続) | 本文を読むにはMESSAGE_CONTENT(特権intent)が要る。100サーバーを超えると審査 |
| Slack | アプリを入れたワークスペースで、招待されたチャンネル | Events API | 配布するアプリは履歴の取得が毎分1回・15件に制限される。自分の組織用に作る内部アプリは対象外 |
| Google ドキュメント/スライド | drive.file なら、ユーザーが選んだファイルかアプリに共有したファイルだけ | changes.list で差分を取る。push通知は公開HTTPSが要り、1週間ごとに張り直す | drive.readonly などの制限付きスコープは、データを保存するとセキュリティ評価が要る |
| Notion | 連携に共有したページと、その子ページ | webhook(変更されたページのIDだけが届く)。受け口は公開HTTPS | 内部連携はワークスペースのオーナーが作る |

出典は次のとおり。Slackの履歴取得の制限は、公式の変更履歴で一次情報を確かめた(2025-05-29以降に作られ、Marketplace外で商用配布されるアプリが対象。内部アプリは影響なし。https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps )。Google(https://developers.google.com/workspace/drive/api/guides/api-specific-auth )とNotion(https://developers.notion.com/docs/authorization 、https://developers.notion.com/reference/webhooks )の権限と変更検知は、調査担当が公式文書から要約したものである。

Discordの開発者ポリシー(施行 2024-07-08、https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy 。2026-10-20 のウェブアーカイブの保存版で原文を確認)には、設計に効く条項が3つある。第15条は、APIで得たデータを、表明した機能に必要な範囲でしか使わないこと。第16条は「Do not use API Data to: profile Discord users, their identities, or their relationships with other users」。第21条は、Discordの許可なくメッセージ本文を機械学習やAIモデル(LLMを含む)の訓練に使わないこと。

会話の発言から人の詳しさを推定する処理は、第16条の「プロファイリング」に当たるおそれがある。条文からは範囲を読み切れないが、違反と判断されればボットの停止もありうる。2026-10-27、ユーザーはこの危険を承知のうえで、参加登録していない人の発言も推薦の根拠に使うと決めた。設計では次の手当てを入れる。この扱いは組織ごとの設定(`expertise_from_messages`、既定はオフ)にし、ユーザーの組織ではオンにする。本人が `/tekijin optout` を打てば、その人の発言を根拠から外し、推定データを消す。推定した詳しさは組織の外に出さない。推薦の理由も、質問した本人にしか見せない。経緯はADRに残す。第21条については、TEKIJINは学習を行わず、推論と検索にだけ使うので該当しない。

日本の個人情報保護法との関係では、利用目的の特定と公表、本人からの利用停止・削除の請求への対応、海外のLLM APIに会話を送る場合の整理が論点になる。これは一般論の整理で、任意団体がどこまで義務を負うかは確かめていない。設計としては、LLMはローカル(evo-x2)を既定にし、外部APIを使うときは組織の明示的な同意を条件にする。

## 4. 設計

### 4.1 全体の流れ

```
取り込み                           知識化                       質問への応答
Discordのチャンネル ─┐            文書の断片 ─→ 知識の下書き     /ask
Google ドキュメント ─┼→ 取り込み項目 ─→ 断片+埋め込み          │
Googleスライド ─────┤   (出典・作者・   会話 ─→ 解決した話の下書き  ├→ 知識・断片・会話を検索
Notionページ ───────┘    更新日)       自己紹介 ─→ 本人の申告    ├→ 根拠があれば出典付きで答える
                                                              └→ 無ければ詳しい人を推薦して依頼
                                     確認 ─→ 確認済みの知識 ←── 依頼された人の回答
```

質問を処理するグラフ(聞き返し、経路の判定、自己回答、取次ぎ、辞退からの再推薦)はそのまま使う。作り替えるのは、データの持ち方、取り込み、人の推薦の3つである。

### 4.2 組織とメンバー

`organizations` テーブルを新設し、組織に属するデータの表には、すべて `org_id` を持たせる。最初は組織が1つなので値は常に同じになるが、あとから列を足すより安い。BM25のキャッシュ、語彙、経路の閾値も組織ごとに持つ。

`employees` は `members` に置き換える。必須なのは表示名と組織だけにする。部署・役職・支店・入社日・パスワードは削る。人と外部アカウントの対応は `identities` テーブル(`member_id`、`provider`、`external_id`、`org_id`)で持つ。providerはdiscord、slack、google、notionの4つ。DiscordのD1で設定ファイルに書いていた対応表は、この表に置き換える。

Discordサーバーのメンバーは、全員を `members` に持つ。ボットがメンバー一覧を読んで作り、参加や退出に合わせて更新する。登録の手続きが無くても、誰でも質問でき、推薦の対象にもなる。詳しさの根拠には、自己紹介スライドや文書の作者といったDiscordの外のデータに加え、組織の設定がオンなら会話の発言も使う(3章)。

`/tekijin join` で参加を登録すると、その人にWebのアカウントが発行される。DiscordのOAuthでログインでき、Web画面と知識追加の機能(4.3節)を使えるようになる。`/tekijin optout` を打った人は、推薦の対象から外れ、その人を根拠にした推定データは消える。発言は知識の材料としては残るが、作者を辿れないようにする。

Web画面は独立した機能として全部残す。Discordを使わない人も、Webから質問、依頼への回答、知識の追加と確認ができる。認証はDiscordのOAuthを主にし、今のメールとパスワードのログインは管理者用に残す。

### 4.3 取り込み

取り込んだものは、種類を問わず `source_items` に入れる(provider、外部ID、URL、題名、作者のmember_id、更新日時、本文のハッシュ)。本文は `chunks` に分けて埋め込みを付ける。今の `documents` は題名と本文を1本のベクトルにしており、分割が無い。マニュアルや引継ぎ書のような長い文書では、それでは検索が効かない。会話は `messages` テーブルに入れる(チャンネル、スレッド、作者、時刻、本文)。

最初に作るのはDiscordで、ボットが読めるチャンネルをすべて取り込む(ユーザーの組織では全チャンネルを対象にすると決めた)。取り込まないチャンネルは、管理者が除外の一覧で指定する。過去の履歴は最初に1回読み込み、そのあとはGatewayで新しい投稿を受ける。ボットはすでにGatewayに常時接続しているので、公開URLは要らない。

文書の入口は3つにする。いちばん手軽なのは知識追加で、メンバーが `/tekijin add` に文章と、あれば置き場所のURLを付けて送る。長い文書はファイルの添付でも受け付ける。2つ目は、管理者がWebの画面から文書を追加する方法。3つ目は、Googleのサービスアカウントへの共有である。サービスアカウントは、Googleが発行するボット用のアカウントで、メールアドレスを持つ。文書やフォルダをこのアドレスに共有してもらえば、TEKIJINはその文書の本文を files.export で読み、changes.list を定期的に呼んで更新を拾う。OAuthの審査も、7日で切れるトークンの問題も起きない。ユーザーは組織のGoogleアカウントの管理権限を持たないので、Googleの組織全体からの一括取り込みは考えない。知識追加で送られた文書は、置き場所のURLを出典として持ち、中身は送られた時点のものとする。

Notionは、管理者がワークスペースの内部連携を作り、取り込むページを共有する。変更は定期的な取得で拾う。webhookは公開HTTPSの受け口が要るので、Cloudflare Tunnelで受け口を用意してから考える。

取得、ページ送り、レート制限への対応はOnyx(MITライセンスの部分)のコネクタを参考にする。Onyxを丸ごと取り込むことはしない。TEKIJINの取次ぎや知識化と、Onyxの検索の仕組みは別物で、依存が重くなりすぎるためだ(推測。Onyxの構成の重さは測っていない)。

取り込んだものには、メンバーが削除を求められる窓口を作る。Discordで消された投稿は、Gatewayの削除イベントを受けてTEKIJINからも消す。その投稿から作った知識の下書きは、出典を失ったものとして確認待ちに戻す。

### 4.4 知識

知識の単位は、知識化の調査で推薦されたKCS(Knowledge-Centered Service)の形に寄せる。今の `knowledge_units` は「状況・打ち手・結果」の3つ組で、結果が空のものばかりになった(研究Aの1回目)。

| 項目 | 内容 |
|---|---|
| kind | case(困りごとと解決)、procedure(手順)、fact(事実・決まりごと)、decision(決めたことと理由) |
| issue | 困りごと、または問い。質問者の言葉に近い形で書く |
| environment | どの場面で成り立つか(活動、ツール、時期など)。任意 |
| resolution | 答え。空のものは回答に使わない |
| cause | 原因。任意 |
| state | wip(答えが無い)、draft(下書き)、verified(確認済み)、retired(古くなった) |
| reuse_count、last_used_at | 回答に使った回数と最後に使った日時 |
| superseded_by | 置き換えた先の知識 |

出典は `knowledge_sources`(知識と取り込み項目・メッセージの対応表)に分ける。今は「1出典から1単位」の制約があるが、これを外し、1つの引継ぎ書から複数の手順を作れるようにする。

回答に使うのは、確認済み(verified)の知識だけにする。resolutionが空ならwipに置き、回答には使わない。これで「この知識で答えられるか」の判定のかなりの部分を、判断器ではなく項目の有無で決められる。確認の手間は、よく使われる下書きから順に管理者に見せることで減らす。

知識の作り方は情報源ごとに変える。マニュアルと引継ぎ書からは、手順(procedure)と事実(fact)を作る。会話からは、解決したスレッド(チェックマークのリアクションや「ありがとう」で解決を捕まえる仕組みがすでにある)だけを事例(case)にする。依頼された人の回答は、事例の下書きにする。

### 4.5 質問への答え方

今のC1(意図の解析)は、22語の語彙をLLMの出力の選択肢として強制している。この語彙を消し、C1には「答えるべき質問か」「聞き返しが要るか」だけを判断させる。話題のラベルは、組織ごとに取り込んだ文書から候補を作り、管理者が整える形にする(任意)。ラベルが無くても検索と推薦は動くようにする。

検索は、今のpgvectorとBM25の組み合わせを使い、対象を「確認済みの知識」「文書の断片」「会話」の3つにする。日報の検索は外す。経路の判定(自分で答えるか、人へ繋ぐか)の閾値は、新しい評価データで調整し直す。

### 4.6 詳しい人の推薦

今のC6は、資格・案件・スキル・日報を22語の語彙で突き合わせて点数を付けている。新しい前提では、これらの根拠がどれも存在しない。

推薦は「根拠を先に探し、その作者に辿る」方式に変える。質問に近い文書の断片、会話での回答、確認済みの知識を探し、それを書いた人や答えた人に点数を集める。専門家探しの研究(Balog ら、SIGIR 2006、https://doi.org/10.1145/1148170.1148181 )で、人ごとに知識をモデル化する方式より成績がよかったと報告されている方式である。今のC6にある、質問と過去の回答の意味の近さ(qsim)、回答の質、負荷の調整はそのまま使える。

根拠には種類を付けて分けて持つ。自己紹介スライドや `/tekijin join` で書いた自己申告、文書の作者、会話での回答、TEKIJIN経由で依頼に答えた実績の4種類である。推薦の理由として「○○のマニュアルを書いた」「△△の質問に答えた」のように出典を見せる。推薦の対象はサーバーのメンバー全員で、`/tekijin optout` を打った人だけを外す(4.2節)。会話の発言を根拠に使うのは、組織の設定がオンのときに限る(3章)。

### 4.7 評価

87行の評価セットは使えなくなる。正解を名簿と日報から作っているためだ。代わりに2つ用意する。

1つは、架空のサークル1つ分の合成データである。メンバー15〜30人ほどで、Discordの会話、自己紹介スライド、企画書、マニュアル、引継ぎ書を合成する。開発中の回帰テストと、閾値の調整に使う。もう1つは、ユーザーの組織での小さな正解集(30〜50問)である。メンバーの同意を取ってから、実際の質問と「正しい答え・答えられる人」を人手で付ける。合成データで決めた閾値が実データでも通じるかを確かめる。

測る指標は、答えたときに出典が正しい割合、答えるべきでない質問に答えなかった割合、人への推薦で正しい人が3位以内に入る割合の3つにする。

### 4.8 今のコードの扱い

洗い出しの結果、部品ごとの扱いは次のとおり。

| 扱い | 部品 |
|---|---|
| そのまま使う | 質問処理グラフの骨格(聞き返し、取次ぎ、辞退からの再推薦)、検索の仕組み(pgvector、BM25、RRF)、自己回答の安全策(出典の付与、根拠の判定)、知識のレビューの流れ、ChannelNotifier、チェックマークでの解決の捕捉、認証まわりの防御 |
| 一般化する | 社員→メンバー、文書(分割と出典の追加)、知識単位(KCSの形)、C1(語彙を外す)、C5の閾値(調整し直す)、C6(根拠を差し替える)、Slack連携(名簿が先にある前提を外す)、Discordの対応表(identitiesへ) |
| 消す | 日報とその機能、資格・スキル・案件、支店と距離、22語の語彙と業種別の対応表、会社の合成データと87行の評価セット、それに依存する研究用スクリプト |

DBは今 `create_all` 方式で、マイグレーションの仕組みが無い。研究用DBのほかに守るデータは無いので、今回はスキーマを壊して作り直す。会社向けの最後の状態には `company-v1` というタグを付けて残し、デモや面接の説明ではそれを使う。

## 5. 進め方

一度に作り替えると、途中で何も動かない期間が長くなる。そこで、新しい前提で質問に答えられる最小の形を先に作り、そこへ順に足していく。

| 段階 | 内容 | できること |
|---|---|---|
| R0 | この設計の確定、`company-v1` タグ、ADRに方針を記録 | 判断の記録が残る |
| R1 | organizations、members(サーバーのメンバー一覧から作る)、identities、`/tekijin join`(Webアカウントの発行)と `/tekijin optout`。Discordの対応表を置き換える | 設定ファイルを書かずに、サーバーの誰もが質問できる |
| R2 | 取り込みの共通部分(source_items、chunks、messages)、Discordの全チャンネル取り込み、知識追加(`/tekijin add` とWebからの追加)。架空のサークルの合成データ | 取り込んだ会話と追加した文書から検索できる |
| R3 | C1から語彙を外し、検索の対象を新しい表に替える。日報・資格・支店を削除する | 新しい前提で、出典付きで答えられる |
| R4 | Googleのサービスアカウント経由とNotionの取り込み(定期取得) | 共有された文書を自動で取り込める |
| R5 | 推薦の作り直し(根拠から作者へ)と自己紹介の取り込み | 答えられない質問を人へ繋げる |
| R6 | KCS形式の知識、Discordでの確認ボタン、依頼と回答のスレッド(旧計画のD2〜D4) | 回答が知識に戻る |
| R7 | 実組織での正解集と閾値の調整、Slackの一般化 | 実データでの品質が分かる |

旧計画(2026-10-21)の段階1・2と研究テーマA・D、DiscordのD2〜D4は、この表に吸収する。研究テーマA(知識回答を出すかの判定)は、R6でKCS形式の知識ができてから、新しいデータで比べ直す。

## 6. ユーザーが決めたこと

最初の案で挙げた5つの論点は、2026-10-27 にユーザーが次のとおり決めた。

| 論点 | 決定 |
|---|---|
| 文書の入口 | ユーザーは組織のGoogleアカウントの管理権限を持たない。サービスアカウントへの共有は残しつつ、主な入口は管理者によるWebからの追加と、メンバーがスラッシュコマンドで文章と置き場所を送る知識追加にする |
| 推薦の対象 | 参加登録していない人も含め、サーバーのメンバー全員を対象にする。会話の発言も詳しさの根拠に使う(第16条の危険を承知のうえ。手当ては3章)。参加登録した人にはWebのアカウントを発行する |
| 取り込みの範囲 | 試す組織では全チャンネル・全文書。メンバーへの告知はユーザーが行う |
| Web画面 | 独立した機能として全部残す |
| 会社向けの版 | `company-v1` タグで残し、developからは消す |

## 7. リスク

いちばん大きいのは、組織の会話が雑談中心で、知識にできる部分が少ない可能性である。研究Aの1回目では、日報から作った知識が薄すぎて判定が機能しなかった。会話も同じことになりうる。R2で実組織の会話を取り込んだ時点で、知識になりそうな会話の割合を数え、少なければ文書(R4)を先にする。

次に、推薦の根拠が集まるまで時間がかかる問題がある。始めたばかりの組織では、回答の実績が無い。自己紹介スライドと `/tekijin join` での自己申告が、最初の根拠になる。

最後に、作り替えの規模が大きいことである。R1からR3までは既存の機能を壊しながら進めるので、テストの書き換えが多くなる。各段階をPRに分け、段階の終わりごとに全テストが通る状態を保つ。
