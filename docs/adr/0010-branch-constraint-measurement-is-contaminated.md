# ADR-0010: 拠点制約（#83）の測定はプロンプト適合で汚染されている — 数字は使えない

- ステータス: 承認（**有効化の判断は保留**）。2026-11-04 に #93 で拠点制約と `proximity` をコードから消した（一般組織向けへの作り替え、ADR-0012）。実装は `company-v1` タグに残る
- 日付: 2026-08-26
- 決定者: A チーム（AIレビューの指摘を実データで確認した結果）
- 関連: ADR-0008（系統②の Hit@3 天井）/ ADR-0009（候補集合を広げる案の棄却）/ #83 / #80 / #158 / #296 / #384

## 背景

#83 は「明示された拠点は加点ではなく**条件**として扱う」案。実装して DGX でフルグラフ E2E の
3反復ペア比較を取ったところ、**非常に強い結果**が出た:

| 指標 | base | 拠点制約 ON | 平均差 |
|---|---|---|---|
| **Hit@3** | 0.7626 [0.758 0.773 0.758] | **0.8232** [0.818 0.833 0.818] | **+0.0606** |
| Top1 / R@3 / MRR | 0.6111 / 0.6052 / 0.6835 | 0.6667 / 0.6835 / 0.7424 | +0.056 / +0.078 / +0.059 |
| RouteAccuracy | 0.7639 ×3 | 0.7639 ×3 | ±0 |
| decision recall: route（person） | 1.000 ×3 | 1.000 ×3 | ±0 |
| self_answer / source recall | 0.478 / 0.207 | 0.478 / 0.207 | ±0 |

3反復とも差がきっかり +0.0606（4行/66）。C1 の抽出精度も別途 全87行で測り、
**制約つき 15/15（recall 1.000）／制約なし 72件中 誤検出 1件（0.014）**。
Hit@3 0.8232 は ADR-0008 の天井（≈0.72–0.78）を超える。

**この数字は使えない。**

## 決定

**既定 OFF を維持する。上の数字を「拠点制約の効果」として引用しない。**

### 理由: C1 プロンプトが、採点される行に合わせて書かれている

プロンプトは**評価セットの制約行を読んだあとに**書かれた。その結果:

1. **特別ルールが、素朴な抽出器の失敗行と1対1で対応している。**
   `docs/benchmarks/ablation/robustness_results.json` の `constraint_extraction` は、
   部分一致ベースの素朴な抽出器が落とす行を id で記録している:
   **11, 13, 15, 17, 19, 21, 24, 25**（recall 0.467）。
   新プロンプトの2つの特別ルールは、これをそのまま覆う:
   - 「『本部』は本社」 → 13 / 15 / 17
   - 「地方名で言われたら括弧内の地域から対応する拠点に読み替える」 → 11 / 19 / 21 / 24 / 25
2. **否定例が評価行の逐語コピー。** プロンプトの
   「例: 『大阪の事例があれば参考にしたい』は希望ではないので null」は、
   **eval id=1 の文末そのもの**（`note` に「拠点制約ではない。誤検出の検出用」と書かれている行）。

つまり recall 1.000 も +0.0606 も、**その15行に合わせて書いたプロンプトを、その15行で採点した値**。
これは **#384 で「C1 few-shot で Hit@3 0.803」を撤回したときと同じ欠陥**（eval leakage）。

### 補足: gold の作られ方も効果を底上げしている

制約つき15行の `gold_experts` は**全員が希望拠点にいる**（`build_eval_v2` がそう作っている）。
「拠点で絞ると制約行の R@3 が上がる」は、構成上ほぼ自明に近い。

### 補足: そもそも新しいコード経路が要るのかも未確定

committed のベンチ（`robustness_results.json`）では

| 扱い | 制約つき | 全体 |
|---|---|---|
| 拠点一致を**加点** | 0.9333 | 0.7727 |
| 拠点で**絞ってから並べる** | 0.9333 | 0.7727 |

**同値**。`config.py` に一時期書いていた「`proximity` を 0.40 にすると 0.900 まで届くが
制約の無い質問すべてを歪める」は、**リポジトリのどこにも測定が無い**（撤回済み）。
`Weights.proximity` の1行変更で同じ効果が得られるなら、新しい分岐を C6 に足す理由は弱い。

## 影響

- **`branch_constraint_enabled` は既定 False。** 実装・テスト・ハーネスのフラグは残す
  （きれいに測り直せる状態にしておくため）。
- **有効化の前提**（#437 で追跡）:
  1. **プロンプトを見ずに書かれた held-out の制約表現**で抽出 recall と誤検出率を測る。
     現在の15行は「プロンプトが知っている行」なので使えない。
  2. **誤検出をもっと多くのデコイで測る。** 制約なし72行のうちデコイはわずか3行で、
     「抽出しがち」なプロンプトでも集計 Hit@3 では無害に見えてしまう
     （#357 の knowledge false-fire が直接測って初めて出たのと同じ形）。
  3. **加点（`proximity` 引き上げ）との比較を実測でやり直す。** 同値なら1行の設定変更を採る。
- `research_fullgraph_eval.py` は `constraint_branch` について**何も記録していない**
  （抽出 recall も誤検出率も、制約が満たされたかも）。上の 1・2 を測るには
  `scripts/research_robustness.py::constraint_extraction` を素朴な抽出器から C1 に向け直すのが早い。

## 教訓

**「プロンプトを書く前に、そのプロンプトが採点される行を読んでいないか」を毎回確認する。**
今回は測定手順（3反復ペア比較・経路非退行の確認・機構の局在化）はすべて正しく踏んでいて、
それでも結論は使えなかった。手順の厳密さは、汚染された入力を救わない。
